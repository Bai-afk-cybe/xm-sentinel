# 厦门短临预警哨兵（云端版）

跑在 GitHub Actions 上的厦门雷达哨兵：每 6 分钟拉 NMC 华东雷达拼图，按《厦门短临预警台》
同源五档判据定级，触发即推送（方糖 → 微信；ntfy → 各订阅者专属主题）。
**再加一条每日复盘**：每天早上 9:00 自动把「前一天报了什么」和「后来实际发生了什么」对账，
生成报告并推到你手机。

**判分不再只靠雷达自证**：同时采集**地面降水实况**（`truth.jsonl`）作为独立真值——
雷达看到回波 ≠ 地面真的下雨。没有它，「报了却滴雨未下」的空报永远查不出来。

**电脑关机也照常运行**——这是本仓库存在的全部意义。

## 两个工作流

| 工作流 | 触发 | 干什么 | 产出 |
|---|---|---|---|
| `xm-sentinel` | 每 6 分钟 | 拉帧 → 定级 → 推送预警；记录判定流水 | 推送、`.state.json`、`verify.jsonl` |
| `xm-daily-review` | 每天 UTC 01:00（北京 09:00） | 复盘前一日：回验打分 → 生成报告 → 推手机摘要 | `review/<日期>.md`、`review/latest.md` |

> ⚠️ GitHub 的定时任务在整点高峰期常延迟 **5~30 分钟**，所以 9:00 的复盘实际约
> **09:05~09:35** 到达；哨兵的 6 分钟同理（实际 6~16 分钟）。

## 首次部署（只做一次）

1. 登录 github.com → 右上角 + → New repository
   - 名字：`xm-sentinel`（随便取，下同）
   - 选 **Public**（公开仓库 Actions 免费不限量）
   - **不要**勾选 README / .gitignore / license，直接 Create
2. 配置方糖密钥：仓库页 → Settings → Secrets and variables → Actions
   → New repository secret → Name 填 `XM_FTQQ_KEY`，Secret 填方糖 SendKey（SCT 开头那串）
2.5 **（推荐，可选）** 同页面再加一个 secret：Name 填 `XM_CAIYUN_TOKEN`，值填彩云天气
   API token。不配也能跑——会自动回落 Open-Meteo（无需 key，但是**模式值、分辨率粗**）；
   配了则拿到 **1km 实测级**地面真值，准确率统计才真正可信。
   备用实测源：也可改用和风——加 `XM_QWEATHER_KEY`（可选 `XM_QWEATHER_HOST`）。优先级
   彩云 ＞ 和风 ＞ Open-Meteo，两个 key 都不配时自动回落 Open-Meteo。
3. 上传代码：仓库主页 → "uploading an existing file" 链接
   → 把本目录里的全部内容拖进去（**包含 .github 文件夹**）→ Commit changes
4. 启用 Actions：仓库 Actions 标签页 → 如提示信任，点 "I understand…enable"
5. 试跑两个工作流：Actions → 分别选 `xm-sentinel` / `xm-daily-review` → Run workflow
   → 绿勾 = 通了；红叉 = 点进去把报错日志发出来

## 🔧 升级（改判据后怎么更新仓库）

**只替换变动的文件，别整目录覆盖**——尤其**不要**把本目录里的 `.state.json` 传上去，
覆盖云端当前状态会导致重复推送/漏推。

网页操作：仓库主页 → 点进目标文件 → 右上角铅笔图标 → 粘贴新内容 → Commit changes。
新建文件（如首次加 `daily_review.py`）：主页 → Add file → Create new file → 文件名里
**直接写带路径的名字**（如 `.github/workflows/daily-review.yml`），GitHub 会自动建目录。

传完后：Actions → 对应工作流 → Run workflow → Run，看是否绿勾。

## ⚠️ 密钥安全（务必处理）

1. **旧版曾把方糖 SendKey 明文写在 `xm_sentinel.py` 里**，而本仓库是 Public ⇒
   **任何人都能冒充哨兵往你微信推任意消息**。本目录已改为读环境变量 `XM_FTQQ_KEY`
   （未配置则通道自动禁用）。**请到方糖后台重置 SendKey，并更新 GitHub Secrets。**
2. **`sentinel.log` 含订阅者的 ntfy 主题名**（主题名等同口令，拿到就能看/发该主题消息），
   目前仓库里还留着一份 ⇒ 请在网页上**删除该文件**，`.gitignore` 已把它排除。
3. 想彻底私密：把仓库改成 Private。私有仓库的 Actions 每月有 2000 分钟免费额度——
   按本哨兵用量（每 6 分钟 × 约 1 分钟 + 每日复盘）**约 7500 分钟/月，会超**，
   所以保持 Public 更合适，靠"不提交任何密钥"来保证安全。

## 地面降水实况（准确率的地基）

判分曾经只用雷达自证：10 km 内峰值 ≥40 dBZ 就算「发生了影响」。但**雷达看到回波 ≠ 地面有雨**。
2026-10-02 10:06 牡丹国际大酒店被判「较高预警」，而该点位地面实测只有 0.1 mm/h（滴雨未下）——
用雷达检验雷达，这类空报永远查不出来。

现在 `verify_closure.score()` 的判分优先级：

1. **地面实况（优先）**：事件后 30 分钟内该点位地面雨量 ≥0.5 mm/h → 认定真的下到了地上
2. **雷达自证（回落）**：窗口内没有任何地面采样时才用

数据源按优先级自动选择（环境变量 `XM_TRUTH_SOURCE` 可强制指定）：

| 源 | 分辨率 | 性质 | 启用方式 |
|---|---|---|---|
| 彩云 `caiyun` | 1 km，分钟级 | 雷达+地面站融合，**实测级** | 配 `XM_CAIYUN_TOKEN` |
| 和风 `qweather` | 1 km | 实测级 | 配 `XM_QWEATHER_KEY` |
| Open-Meteo `openmeteo` | 网格 ~5-11 km | **模式值，非实测** | 无需配置（兜底） |

> ⚠️ Open-Meteo 判「有雨」较可信，判「无雨」存在**低估风险**（模式对对流偏干、落区被平滑）。
> 要真正冲高准确率，请配彩云 token。

**采样策略（额度自适应）**：无预警时每 30 分钟一轮（抓漏报的对照组），有预警点位时每 6 分钟
一轮（验证空报）。彩云完成**个人认证**后免费额度为 **10000 次/天**，13 个点位按此策略
约 620~830 次/天，余量十倍以上。

> ⚠️ 彩云免费档有**突发限流**（背靠背请求即 429），所以逐点请求之间强制留
> `XM_CAIYUN_MIN_INTERVAL`（默认 1.2 s），并对 429 做退避重试 `XM_CAIYUN_RETRY`（默认 3 次）。
> 这两个值一般不用动；把间隔调小只会换来大面积 429、点位被判「无数据」。

**自愈**：若某次预警缺地面证据（本地关机 / 云端故障导致漏采），每日复盘会自动用
Open-Meteo **回溯补采过去 96 小时**再重新判分——地面真值不必实时攒，事后能补。

> ⚠️ 但回溯**只能用 Open-Meteo**（模式值）：彩云实时接口只给「此刻」，免费档没有历史查询。
> 因此**已过去的事件无法再升级为实测口径**——实测级判定从接入彩云那一刻起才生效。

**距离旁证（只提示，不改档）**：彩云的 `precipitation.nearest` 会给出「离该点最近的降雨云团
有多远」。它是一条**独立于 NMC 的链路**（彩云自建雷达拼图 vs 中央气象台 ECREF），与哨兵
自算的最近回波距离正好互为旁证。实测 13 个点位（`_probe_caiyun_dist.py`）：两者差
−1.7 ~ +1.8 km、均值 +0.75 km，**远近排序完全一致**（都认出九节礁最远、远海/新海达最近）。

- 比对面取 `d40`（最近 ≥40 dBZ 回波距离）——它才与彩云同口径；比 `dist`（35 dBZ）会偏约 2 km
- 允许差 `XM_NEAREST_TOL_KM`（默认 5 km，取实测离散度的约 3 倍余量）
- 差得远只在报告 note 里追加一条 `◎ …距离判据存疑，需人工核`
- **绝不参与定级**：旁证口径未完全标定，宁可少判也不据旁证改档

**判分还会区分「报准」与「报得过头」**：地面有雨但雨强远低于该档位期望
（较高 ≥5、高等 ≥15、特高 ≥30、极高 ≥50 mm/h）时，报告单列为「报得过头」，
避免用一场毛毛雨去确认一次 40 dBZ 的强对流预警。

## 与本地版的关系

- 判据同源：`xm_sentinel.py` 由本地版复制而来，唯一改动是方糖 SendKey 从环境变量读取。
- **改判据时两边要同步改**（本地版和本目录），或者干脆只改这边、把本地计划任务停掉。
  ⚠️ 两边同时跑会出现**双份推送**——建议只保留云端为唯一生产端。
- `.state.json` 会随每轮运行自动提交回来，作为下一轮的"记忆"
  （last_push 节流、near5 临近确认标记、各订阅者状态分片）。
- 首次运行前仓库里没有 `.state.json` 属正常：第一轮会自动生成。

## 已知差异（相对本地计划任务版）

- GitHub 定时器标称 6 分钟，实际可能推迟 3~10 分钟（高峰期更明显）——
  比"电脑关机完全没推送"强得多，但比本地准点 6 分钟略钝。
- 每轮运行会留下一条 state 提交，仓库历史会长，属正常。
- GitHub 定时工作流在仓库 60 天无活动后会被平台自动停用——本哨兵每轮都提交状态，
  不会触发；若长期停用后再启用，去 Actions 页面手动 enable 一次即可。
